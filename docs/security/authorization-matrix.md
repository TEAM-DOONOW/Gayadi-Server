# API 권한과 IDOR/BOLA 검증 기준

## 기본 원칙

- 사용자 ID는 요청 본문이나 query parameter가 아니라 인증된 Access Token의 `sub`에서 가져온다.
- 경로의 `tripId`, `scheduleId`, `expenseId`, `friendshipId` 등은 식별자일 뿐 권한 증명이 아니다.
- Controller 인증과 별개로 Service 또는 Repository 조회 조건에서 소유자·참여자 관계를 검증한다.
- 다른 사용자의 유효한 ID를 넣어도 데이터가 조회·수정·삭제되지 않아야 한다.
- 존재 여부 노출이 위험한 사용자 소유 자원은 정책에 따라 403 또는 404로 일관되게 거부한다.

| Favorite·Friendship | - | 본인 찜과 본인이 당사자인 친구 관계 | - | - |
| Trip | - | 본인 여행 목록 | 여행 상세 조회 | 상태 변경·삭제·참여자 관리 |
| Schedule·Plan·Route | - | - | 조회 및 정책상 허용된 편집 | 여행 구조 변경 |

## 자동 검증 범위

`AuthorizationIntegrationTests`는 다음 공격을 검증한다.

- 요청 본문의 위조된 `ownerId`가 무시되고 인증 사용자로 소유자가 결정되는지
- 비참여자가 다른 여행 ID로 여행 상세와 상태 변경에 접근할 수 없는지
- 비참여자가 해당 여행의 일정·경비·대시보드 ID를 직접 대입해도 접근할 수 없는지
- 삭제된 여행의 하위 자원에 다시 접근할 수 없는지

새로운 자원 ID 기반 API를 추가할 때는 소유자 성공, 참여자 허용 범위, 비참여자 거부, 다른 상위 자원과 하위 ID를 섞은 요청을 함께 테스트한다.
