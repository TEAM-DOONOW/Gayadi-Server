# DB 개인정보 보호 기준

## 데이터 처리표

| 데이터 | 현재 처리 | 목표 처리 |
|---|---|---|
| 비밀번호 | BCrypt 단방향 해시 | 유지하며 원문·복호화 암호화 금지 |
| Refresh Token | Redis에 SHA-256 해시와 TTL | 유지하며 원문 저장 금지 |
| 사용자 이메일 | 소문자 평문, unique 검색 | AEAD 암호문 + 별도 HMAC 검색 인덱스 |
| 소셜 계정 이메일 | 평문 | 불필요하면 미수집, 필요하면 AEAD 암호화 |
| 문의 연락 이메일 | 평문 | AEAD 암호화 |
| 장소 전화번호·주소 | 공개 장소 정보 | 개인정보와 공공정보를 분류한 뒤 개인정보만 암호화 |
| 주민등록번호·영구 기기 식별자 | 미수집 | 수집 금지 유지 |

## 암호화 전환 조건

AES-256-GCM 또는 동등한 인증 암호화를 사용하고 `keyVersion`, nonce, ciphertext와 authentication tag를 저장한다. 키는 Git·DB·컨테이너 이미지와 분리된 KMS/Secret Manager에서 주입한다. 동일 키로 암호화용과 검색 HMAC용을 겸용하지 않는다.

이메일은 로그인 정확 검색과 unique 제약에 사용되므로 암호문을 직접 검색하지 않는다. 정규화한 이메일에 HMAC-SHA-256을 적용한 검색 인덱스를 별도 컬럼에 두고, 암호문은 프로필 반환 용도로만 복호화한다.

## 안전한 배포 순서

1. KMS key와 독립된 검색 HMAC key를 준비한다.
2. nullable 암호문·key version·검색 index 컬럼을 추가한다.
3. 신규 쓰기를 암호문과 검색 index에 이중 기록한다.
4. 기존 데이터를 배치 백필하고 건수·중복을 검증한다.
5. 읽기와 로그인 검색을 신규 컬럼으로 전환한다.
6. rollback 기간 후 평문 컬럼을 제거한다.
7. 이전 key decrypt와 현재 key encrypt가 가능한 상태로 key를 교체한다.

KMS와 복구 절차 없이 애플리케이션 공통키만 추가하는 방식은 데이터 유실과 전체 계정 잠금 위험 때문에 적용하지 않는다.
